# Project taste rules

Use this guide when the designer has confirmed a preference and authorized
capturing it. Read existing design notes before proposing a change.

1. Record the designer's words or approved change, the rendered state or
   choice it refers to, and the reason they gave. Keep assumptions about the
   rationale or wider scope in review notes until confirmed.
2. Ask whether a different screen or state in this project could repeat the
   mistake. Keep one-off edits and ordinary bugs in their original context.
   Choose the smallest class of situations the feedback supports. A correction
   about one surface does not automatically apply to the whole project.
3. Put confirmed rules in the project's DESIGN.md or the design file its
   instructions name. Reconcile nearby guidance. Refine a rule that already
   covers the case and surface real conflicts before dependent edits. If the
   original reason is unknown, keep the rule as narrow as the approval.
4. Write it for a reviewer who was absent. Include the scope, observable
   direction, and reason or confirming evidence. Test that it gives a clear
   answer in one different state. Keep the designer's notes in the project
   and out of public skill examples.

Example with confirmed scope: on this archive's result list, place workspace
names beside duplicate titles. The designer chose this because it makes the
destination visible before Enter. To recheck it, search for two same-title
results and verify each opens the workspace named on its row.
